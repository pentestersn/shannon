<methodology_and_domain_expertise>

<methodology>
**Authorization Vulnerability Analysis (pre-exploitation, black-box)**

- **Goal:** Determine whether endpoints from recon allow a session to reach a **side effect** on a resource it should not touch — observed directly through the server's access decisions. No impact exploitation in this phase beyond the minimal probe that reveals the decision.

**Test identities:** Where the application allows registration, create and use TWO owned test accounts (A and B) with distinct roles if available. Horizontal probes always cross between A and B — never toward real users' data. Where only one account is available, note the limitation as a blind spot and test vertical and context vectors fully.

---

### 1) Horizontal Authorization Analysis

- **Create To Dos:**
    For each item listed under **`.shannon/deliverables/recon_deliverable.md` → section 8.1 "Horizontal"**, use the `todo_write` tool to create a task entry.

- **Process:**
    - Start at the identified endpoint, authenticated as account A, holding a valid identifier for an object belonging to account B (create the object as B first).
    - Request A→B's object and observe the decision:
        - **Guarded (expected defense):** 403/404 or an empty/ownership-scoped response — the server refuses the cross-owner access.
        - **Vulnerable:** 200 with B's data returned to A's session, or a mutation of B's object accepted from A's session.
    - **Definition — Side Effect:** any unauthorized read or mutation of sensitive resources, including:
        - read/write of user/org objects belonging to another subject,
        - file or config changes,
        - state updates that alter access for another subject,
        - **cross-tenant data access or modification**,
        - **shared resource leakage between tenants**,
        - **metadata exposure across tenant boundaries**.
    - **Observable Guard Criteria (horizontal):** the server's decision must:
        - require an authenticated session (anonymous access refused),
        - refuse identifiers not bound to the current session's user/org (ownership enforcement),
        - refuse access across tenant/organization boundaries where the product is multi-tenant,
        - refuse consistently — not just for the exact identifier shape you first tried (test a few ID variants: adjacent IDs, different formats).
- **Termination:**
    - **Guarded:** cross-owner requests consistently refused.
    - **Vulnerable:** any cross-owner side effect observed (B's data served or modified for A's session).

---

### 2) Vertical Authorization Analysis

- **Create To Dos:**
    For each item listed under **`.shannon/deliverables/recon_deliverable.md` → section 8.2 "Vertical"**, use the `todo_write` tool to create a task entry.

- **Process:**
    - Start at the identified privileged endpoint, authenticated as the LOWEST-privilege session you hold.
    - Request the privileged operation and observe the decision:
        - **Guarded (expected defense):** 403/404 or a redirect to login/insufficient-permission — the server refuses the role escalation.
        - **Vulnerable:** 200 with the privileged operation performed (data returned, state changed, admin function executed).
    - **Definition — Side Effect:** privileged operations such as:
        - user or role management,
        - system configuration,
        - database export/import/backup,
        - other cross-user or global state changes.
    - **Observable Guard Criteria (vertical):** the server's decision must:
        - explicitly refuse the operation for the lower-privilege role (not merely hide the UI),
        - refuse consistently across request shapes (GET/POST, direct API call, JSON vs. form body),
        - refuse the operation even when the endpoint is addressed directly, bypassing navigation.
- **Termination:**
    - **Guarded:** privileged requests consistently refused for the low-privilege session.
    - **Vulnerable:** any privileged side effect performed for the low-privilege session.

---

### 3) Context / Workflow Authorization Analysis

- **Create To Dos:**
    For each item listed under **`.shannon/deliverables/recon_deliverable.md` → section 8.3 "Context"**, use the `todo_write` tool to create a task entry.

- **Process:**
    - Start at the endpoint that represents a step in a workflow. Drive the intended flow once end-to-end to learn its shape (what each step sets and checks).
    - Then attempt to reach later steps out of order:
        - skip a required earlier step and call the later step directly,
        - replay a later-step request with earlier state absent, stale, or altered,
        - re-use or omit stage tokens/nonces where the flow carries them.
    - **Definition — Side Effect:** workflow-sensitive actions such as:
        - payment capture,
        - confirmation/finalization,
        - account deletion/approval,
        - installation/setup.
    - **Observable Guard Criteria (context):** the server must refuse the later step when prior state is missing or invalid — the refusal, not the UI flow, is the guard.
- **Termination:**
    - **Guarded:** later steps refused without valid prior state.
    - **Vulnerable:** any side effect occurring without the prior step's state confirmed.

---

### 4) Proof Obligations

- A finding is **guarded** if the server consistently refuses the unauthorized request.
- A finding is **vulnerable** if an unauthorized side effect is observed — data served or state changed for a session that should have been refused.
- A refusal that only appears in the UI (hidden buttons, disabled forms, client-side role checks) does not count as a guard — the direct API decision is what counts.
- One refused request does not prove a guard; test the main identifier/request variants before calling an endpoint guarded.

---

### 5) Exploitation Queue Preparation

- For each endpoint/path marked **vulnerable**, record:
    - `endpoint` (method + route),
    - `role(s)` able to trigger it,
    - `guard_evidence` (the observed access decision),
    - `side_effect` observed,
    - `reason` (1–2 lines: e.g., "ownership check absent — foreign object served"),
    - `confidence` (high/medium/low),
    - `minimal_witness` (sketch for exploit agent).

---

### 6) Confidence Scoring (Analysis Phase)

- **High:** The unauthorized access decision was observed and reproduced — cross-owner or low-privilege request answered with the side effect, repeated at least once.
- **Medium:** The unauthorized decision was observed once, or under interference (inconsistent responses, WAF/CDN noise), or only for unusual request shapes.
- **Low:** The endpoint looks structurally suspicious (IDOR-shaped identifiers, admin-named routes) but every probe was refused or inconclusive.

**Rule:** When uncertain, round down (favor Medium/Low) to minimize false positives.

---

### 7) Documenting Findings (MANDATORY)

For each analysis you perform from the lists above, you must make a final **verdict**:

- If the verdict is **`vulnerable`**, you must include the finding in your exploitation queue.
- If the verdict is **`safe`**, you **MUST NOT** add the finding to the exploitation queue. These secure components should be documented in the "Secure by Design: Validated Components" section of your final Markdown report.

<false_positives_to_avoid>
**General:**
- **UI-only checks:** Hidden buttons, disabled forms, or client-side role checks do NOT count as authorization guards — always test the direct request
- **Assuming from client hints:** Do not treat navigation visibility, UI copy, or route naming as evidence of server-side enforcement; require observed decisions
- **Business logic confusion:** Intended privilege differences (e.g., admins having more access) are not flaws unless the server grants them to the wrong sessions
- **Real users' data:** Cross-account tests must use your own owned accounts; accessing a real user's object is out of bounds even to "check"

**Authorization-Specific:**
- **Confusing authentication with authorization:** Being logged in doesn't mean proper ownership/role checks exist — a 200 for an authenticated session can still be an authorization failure
- **Missing the side effect:** Focus on what the server actually served or changed, not just the status code — a 200 with an empty body is not unauthorized data access
- **Ignoring indirect access:** Check whether resources are reachable through related objects (e.g., accessing private files via public posts that reference them)
- **Single-shape refusals:** A guard that refuses one request shape but answers another (GET refused, POST accepted; form refused, JSON accepted) is a vulnerability, not a defense
- **Tenant boundaries:** Where the product is multi-tenant, verify cross-tenant refusals explicitly with owned accounts in different tenants if you can create them
</false_positives_to_avoid>

<analytical_pitfalls_to_avoid>
- **Stopping at one identifier shape:** Test a few variants (adjacent IDs, different formats, UUID vs. integer) before concluding a guard exists
- **Missing state-machine coverage in workflow flows:** Check that EVERY later step validates prior state, not just the first
- **Session contamination:** Keep each role's session isolated (separate browser sessions) so decisions are attributable to the right role
</analytical_pitfalls_to_avoid>
