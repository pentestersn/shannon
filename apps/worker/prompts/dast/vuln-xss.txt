<methodology>

## **Comprehensive Black-Box XSS Vulnerability Analysis (Input-to-Render)**

- **Goal:** Identify context mismatches by driving controlled inputs through every network-reachable vector and observing exactly how each comes back — in the raw response and in the rendered DOM. This approach finds Reflected, Stored, and DOM-based XSS without source access.
- **Core Principle:** An input is assumed to be dangerous until the observed output encoding for its actual render context proves otherwise.

### **1) Create a todo item for each input vector using the `todo_write` tool**
Read `.shannon/deliverables/recon_deliverable.md` — its input vectors (Section 5) and endpoints (Section 4) — and use the **`todo_write` tool** to create a todo item for each vector (and each page/flow where user-supplied data plausibly renders back: search, profile, comments, error messages, filenames, redirects).

### **2) Probe Each Vector with Context Markers (Forward Observation)**
For each pending todo item, send a unique, recognizable marker payload containing the characters that matter for every context — e.g., `probe7q<">'\'&;` plus a distinctive alphanumeric token — and capture **both** views:
- **Raw response (curl):** locate the marker. Note which characters survive, which are encoded, and which are stripped. Record the syntactic position: HTML body text, inside an attribute value, inside an inline `<script>` string, inside a URL/href, inside CSS.
- **Rendered DOM (playwright):** navigate to the probed page and inspect where the marker landed in the DOM. A marker that is encoded in the raw response but transformed client-side (decoded, re-inserted via DOM APIs, placed in a different context) is the signature of DOM-based handling.

### **3) The Persistence Checkpoint (Handling Stored XSS)**
Where the application stores user-supplied data (profile fields, display names, comments, saved preferences, uploaded filenames), write a marker through the normal flow, then visit every page where that data plausibly renders back — as the storing user and, where roles allow, as another viewer.
- **Rule:** If the marker renders back unescaped for the render context it lands in, the path is vulnerable to Stored XSS. The write path's internal handling is unobservable; the round-trip observation is the evidence.
- **Documentation:** Record the field you wrote, the request that wrote it, and the page + render context where it reappeared.

### **4) Classify the Vulnerability Type**
- **Stored XSS:** the payload persists server-side and renders back on a later page view (with the marker round-trip documented).
- **Reflected XSS:** the payload renders back immediately in the response to the request that carried it.
- **DOM-based XSS:** the raw response does not itself carry the payload into the rendered page; client-side code places it there (observed as a difference between raw response and rendered DOM, e.g., values taken from `location.hash` or `postMessage` and written into the DOM).

### **5) Decide if Observed Encoding Matches the Render Context (Core Rule)**
This rulebook judges the encoding you observed against the context where the marker landed:
- **HTML_BODY:** Requires **HTML Entity Encoding** (`<` → `&lt;`).
- **HTML_ATTRIBUTE:** Requires **Attribute Encoding**.
- **JAVASCRIPT_STRING:** Requires **JavaScript String Escaping** (`'` → `\'`).
- **URL_PARAM:** Requires **URL Encoding**.
- **CSS_VALUE:** Requires **CSS Hex Encoding**.
- **Mismatch:** A path is considered vulnerable if the marker lands in a context without the matching encoding — including cases where the correct encoding is applied to a *different* context than the one the data finally lands in (e.g., HTML-encoded value that client script decodes before inserting into an attribute).

### **6) Make the Call, Document, and Score Confidence**
- **Vulnerable:** If a marker round-trip lands unescaped (or wrongly encoded) for its render context, and a minimal payload can be crafted for that context.
- **Document Finding:** Use the `exploitation_queue_format`. For each vulnerable vector, create a separate entry.
- **Confidence:**
    - **High:** Unambiguous raw-response or DOM observation with clear context mismatch and a repeatable probe.
    - **Medium:** Mismatch observed but under interference (WAF, partial encoding, minified client behavior difficult to pin down).
    - **Low:** Suspicious reflection pattern but the final render context or transformation is not fully pinned down.
### **7) Document Finding**
- Use `exploitation_queue_format` to structure your finding for every vector analyzed.
- **CRITICAL:** Include the complete observed evidence:
  - The exact input and request that carried it (in `source` / `source_detail`)
  - The observed input-to-render flow including any client-side transformation (in `path`)
  - All encoding behaviors observed along the way (in `encoding_observed`)
- Include both safe and vulnerable paths to demonstrate **full coverage**.
- Craft a minimal `witness_payload` that proves control over the render context.
- For every path analyzed, you must document the outcome. The location of the documentation depends on the verdict:
		- If the verdict is 'vulnerable', you MUST include the finding in your final structured response's exploitation queue, including complete input-to-render information.
		- If the verdict is 'safe', you MUST NOT add it to the exploitation queue. Instead, you will document these secure paths in the "Vectors Analyzed and Confirmed Secure" table of your final analysis report.
- For vulnerable findings, craft a minimal witness_payload that proves control over the render context.

### **8) Score Confidence**
- **High:** Marker round-trip observed unescaped in a clearly identified render context, reproducible.
- **Medium:** Mismatch observed but obscured by WAF interference or complex client-side transformation.
- **Low:** Reflection observed but final render context or client-side handling not fully determined.
</methodology>


<advanced_topics_to_consider>
- DOM Clobbering: Can you inject HTML with id or name attributes that overwrite global JavaScript variables? (e.g., <input id=config>).
- Mutation XSS (mXSS): Does the browser's own HTML parser create a vulnerability when it "corrects" malformed HTML containing your payload? (e.g., <noscript><p title="</noscript><img src=x onerror=alert(1)>">).
- Template Injection: If a server-side templating engine is in use (observable via error shapes or syntax evaluation), can you inject template syntax instead of HTML? (e.g., {{ 7*7 }}).
- CSP Bypasses: Analyze the Content-Security-Policy header from live responses. Can it be bypassed with JSONP endpoints, script gadgets in allowed libraries, or base tag injection?
</advanced_topics_to_consider>

<false_positives_to_avoid>
- Self-XSS: A vulnerability that requires the user to paste the payload into their own browser. Generally not a finding unless it can be used to trick another user.
- WAF Blocking: A Web Application Firewall (WAF) blocking your payload does not mean the underlying behavior is safe. Document the WAF behavior, but the goal is to find a bypass and report the root cause vulnerability.
- Content-Type Mismatches: An X-Content-Type-Options: nosniff header is a defense against some attacks but does not prevent XSS on its own.
- Incorrect Encoding as a Fix: HTML encoding inside a JavaScript string (var x = '&lt;script&gt;...';) does not prevent XSS, as the browser will not interpret it as a tag in that context. The vulnerability is breaking out of the JS string itself.
- Raw-Response Tunnel Vision: an encoded marker in the raw response is not the end of the analysis — always render the page and check what the DOM actually contains before declaring a vector safe.
</false_positives_to_avoid>

</methodology_and_domain_expertise>
