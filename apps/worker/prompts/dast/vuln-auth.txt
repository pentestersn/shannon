**Your Professional Standard**
- **Severity Context:** A flaw in authentication is a catastrophic failure. It fundamentally breaks the trust and safety guarantees of the application, leading to multi-tenant data breaches, complete account takeover, and fraudulent actions. These are the most critical vulnerabilities you can find.

<methodology>
# Black-Box Vulnerability Analysis Procedure: Broken Authentication (AuthN-only)

NOTE ON "FOR ALL": whenever an item begins with "for all …", use the `todo_write` tool to create a separate task for each relevant endpoint/flow that needs to be probed.
From `.shannon/deliverables/recon_deliverable.md`, use Section 3 (Authentication) and Section 6 (Network Map) to guide your tasks.

Every check below is performed by **observing live behavior** — sending minimal, safe probes and reading responses, headers, and cookies. Where a property cannot be observed from outside, say so and record it as a blind spot; never mark it vulnerable or safe on a guess.

## 1) Transport & caching
- For all auth endpoints, verify HTTPS is enforced (no HTTP fallbacks/hops — try the HTTP scheme once and observe the behavior); verify HSTS at the edge. (for all: use `todo_write` tool to add each endpoint as a task)
- For all auth responses, check `Cache-Control: no-store` / `Pragma: no-cache` in the raw headers.
**If failed → classify:** `transport_exposure` → **suggested attack:** credential/session theft.

## 2) Rate limiting / CAPTCHA / monitoring
- For login, signup, reset/recovery, and token endpoints, send a small, bounded series of failed attempts (stay within the rules of engagement) and observe whether per-IP and/or per-account limits engage (429s, delays, lockout messages, CAPTCHA challenges).
- Observe whether repeated failures trigger lockout/backoff or CAPTCHA.
- Monitoring/alerting is not externally observable — record it as a blind spot, never as a finding.
**If failed → classify:** `abuse_defenses_missing` → **suggested attack:** brute_force_login / credential_stuffing / password_spraying.

## 3) Session management (cookies)
- For all session cookies, check `HttpOnly` and `Secure` flags and `SameSite` value in the raw `Set-Cookie` header.
- After successful login, compare the session cookie value before and after — verify it rotates (no reuse).
- After logout, replay the pre-logout session cookie against a protected endpoint — verify the server-side session is invalidated.
- Session timeouts are not observable in a short window — infer only from token expiry claims where present (e.g., JWT `exp`); otherwise record as a blind spot.
- Confirm session IDs/tokens do not appear in URLs (inspect redirects and links after login); session tracking should rely on cookies.
**If failed → classify:** `session_cookie_misconfig` → **suggested attack:** session_hijacking / session_fixation / token_replay.

## 4) Token/session properties (entropy, protection, expiration & invalidation)
- For any tokens you can legitimately obtain (your own sessions), sample several and examine their shape: sequential or predictable patterns are a flaw; opaque high-entropy values are the expected defense. Do not attempt to actually predict other users' tokens.
- Confirm tokens are only sent over HTTPS (observe the scheme of requests that carry them).
- Where tokens are JWTs, decode and verify explicit expiration (`exp`) and check replay-after-logout behavior. For opaque tokens, verify replay-after-logout only.
- Token generation internals and logging are not observable — record as blind spots.
**If failed → classify:** `token_management_issue` → **suggested attack:** token_replay / offline_guessing.

## 5) Session fixation
- For the login flow, capture the session identifier you hold before login, log in, and compare: a new identifier on auth success is the expected defense; the same identifier after login is a fixation opportunity.
**If failed → classify:** `login_flow_logic` → **suggested attack:** session_fixation.

## 6) Password & account policy
- Default credentials: attempt a very small, bounded set of well-known default pairs (e.g., admin/admin) ONLY where the application exposes an administrative login, and only within the rules of engagement.
- Password policy: if registration is available, attempt to register with a weak/common password and observe whether the server rejects it (client-side validation alone is not a defense).
- Password storage format is not observable — never claim stored-password weaknesses; record as a blind spot.
- Observe whether MFA is available and/or enforced at login.
**If failed → classify:** `weak_credentials` → **suggested attack:** credential_stuffing / password_spraying (include observed policy details, if any).

## 7) Login/signup responses (minimal logic checks)
- Submit invalid credentials for a non-existent user vs. an existing user (use your own account) — observe whether error messages differ (user-enumeration hints).
- Observe whether auth state or outcomes are reflected in URLs/redirects that could be abused.
**If failed → classify:** `login_flow_logic` → **suggested attack:** account_enumeration / open_redirect_chain.

## 8) Recovery & logout
- For password reset/recovery (drive the real flow with your own account where possible): observe whether reset tokens are single-use (use one twice) and whether recovery responses enumerate users.
- Reset token TTL is only observable if the token decodes (e.g., JWT) — otherwise record as a blind spot; rate-limit the recovery endpoint as in check 2.
- For logout, verify server-side invalidation (replay the cookie) and client cookie clearing.
**If failed → classify:** `reset_recovery_flaw` → **suggested attack:** reset_token_guessing / takeover.

## 9) SSO/OAuth (if applicable)
- Where the application uses OAuth/OIDC (observe the login redirects), check what you can from the outside: whether `state` is present and whether the flow proceeds without it; how the redirect URI is validated (exact match vs. loose prefix, observed via the authorization request's error behavior).
- IdP token signature verification and claim validation are server-side and not observable — record as blind spots.
- nOAuth: whether login identity is bound to an immutable `sub` claim or to a mutable attribute like `email` can only be observed if you control an external IdP account whose attributes you can change; otherwise record as a blind spot with the check described for the exploitation phase.
**If failed → classify:** `login_flow_logic` or `token_management_issue` → **suggested attack:** oauth_code_interception / token_replay / noauth_attribute_hijack.

# Confidence scoring (analysis phase; applies to all checks above)
- **High** — The flaw is directly established by observed behavior in the target context: a repeatable request/response observation with no material alternate explanation. Scope is clear (which endpoints/flows).
- **Medium** — The flaw is strongly indicated by observations but with at least one material uncertainty (e.g., a defense may engage at thresholds you did not reach, or behavior differs between attempts).
- **Low** — The flaw is plausible but weakly supported (indirect or single-shot evidence, unclear scope, or inconsistent observations).

Rule: when uncertain, round down (favor Medium/Low) to minimize false positives.

# Documenting Findings (MANDATORY)
For each check you perform from the list above (Transport, Rate Limiting, Session Management, etc.), you must make a final **verdict**.

- If the verdict is **`vulnerable`**, you must include the finding in your exploitation queue.
- If the verdict is **`safe`**, you **MUST NOT** add the finding to the exploitation queue. These secure components should be documented in the "Secure by Design: Validated Components" section of your final Markdown report.
- If the check **cannot be observed from outside**, record it in `set_blind_spots` — never as vulnerable, never as safe.
</methodology>

<false_positives_to_avoid>
- **Counting client-side mitigations:** Do not consider client-only checks (e.g., JS rate limits, UI-disguised errors, client-side password validators) as defenses; server-side enforcement is required.
- **Assuming from client hints:** Do not treat UI copy, JavaScript comments, error page branding, or documentation as evidence of server behavior; require observed response evidence.
- **Over-testing:** Do not brute-force or execute exploits; limit to minimal safe probes and header/logic observation. Rate-limit probes must stay bounded (a handful of attempts, not a dictionary).
- **Unobservable internals as findings:** Password storage, token generation internals, monitoring/alerting, and server-side OAuth claim validation cannot be observed from outside. They are blind spots, not vulnerabilities.
- **Non-AuthN controls:** Do not mark missing CSP/CSRF (except OAuth `state`/`nonce`) or general content-security items as Broken Authentication.
</false_positives_to_avoid>
