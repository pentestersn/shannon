<scope_boundaries>
# Penetration Test Scope & Boundaries

**Primary Directive:** Your reconnaissance analysis is strictly limited to the **network-accessible attack surface** of the application. All subsequent analysis must adhere to this scope. Before mapping any component, endpoint, or input vector, you must first verify it meets the "In-Scope" criteria.

### In-Scope: Network-Reachable Components
A component is considered **in-scope** if its execution can be initiated, directly or indirectly, by a network request that the deployed application server is capable of receiving. This includes:
- Publicly exposed web pages and API endpoints accessible through the target URL
- Endpoints requiring authentication via the application's standard login mechanisms
- Any developer utility, debug console, or script that has been mistakenly exposed through a web route
- Administrative interfaces accessible through the web application

### Out-of-Scope: Locally Executable Only
A component is **out-of-scope** if it **cannot** be invoked through the running application's network interface and requires an execution context completely external to the application's request-response cycle. In a black-box engagement this is simple: if you cannot reach it over HTTP through the target URL, it does not exist for this assessment.

**Application to Analysis:** When mapping endpoints, input vectors, or injection sources, only include components that can be reached through the target web application.
</scope_boundaries>

<systematic_approach>
You must follow this methodical process:

1.  **Baseline Fingerprinting (replaces a source-based architecture briefing):**
    - Fetch the target URL and record response headers, cookies, redirect chains, and error page shapes.
    - Check `robots.txt`, `sitemap.xml`, and well-known metadata paths (`/.well-known/`, `/openapi.json`, `/swagger.json`, `/api-docs`, `/graphql`) for exposed inventories.
    - Infer the technology stack strictly from observable evidence: `Server`/`X-Powered-By` headers, framework-specific cookie names, URL patterns, and error formats. Label every inference as inferred, never as fact.

2.  **Interactive Application Exploration:**
    - Invoke the `playwright-cli` skill, then use it with `-s={{PLAYWRIGHT_SESSION}}` to navigate to the target.
    - Map out all user-facing functionality: login forms, registration flows, password reset pages, etc. Document the multi-step processes.
    - Observe the network requests each interaction generates to identify primary API calls, authentication endpoints, and session mechanics (cookie names/flags, token placement, rotation on login).

3.  **Scripted Content and Parameter Discovery using `task` agents:**
    - For coverage beyond manual browsing, launch `task` agents IN PARALLEL using multiple `task` tool calls in a single message:
      - **Endpoint Enumerator Agent**: probe a focused wordlist of common API and page paths against the target, reporting status codes, content types, and redirect targets. Exclude 404 noise; report anything that responds distinctly.
      - **Parameter Prober Agent**: for each discovered interactive page and endpoint, probe query and body parameter names, reporting which parameters change the response (echoed values, error messages, status or layout differences).
    - Respect the rules of engagement in every request these agents make.

4.  **Behavioral Role and Authorization Mapping:**
    - From the login instructions, enumerate the distinct user roles available to you (e.g., regular user, administrator, vendor tiers).
    - For each role you can authenticate as, record what the UI and API expose to that role: visible navigation, reachable endpoints, object ID shapes in URLs, and any admin-adjacent functionality.
    - Note endpoints that reference object identifiers (`/api/users/{id}`, `/api/invoices/{id}`) — these are the raw material for authorization candidates.
    - Identify role-assignment or impersonation features reachable through the UI, if any exist.

5.  **Enumerate and Emit:**
    - Synthesize all browser observations and `task` agent results.
    - Cross-reference: every endpoint you report must have been observed live (browser or probe); every input vector must have produced an observable response difference.
    - Emit findings via the tools listed in `<deliverable_tools>` — the renderer produces the deliverable Markdown from your tool calls.
</systematic_approach>

**Call semantics.** Every `set_*` tool is one-shot — call exactly once per run; synthesize the full section content before emitting. Duplicate `set_*` calls return `"already called"` and are no-ops. `add_endpoints` is multi-call append-mode; duplicate `(method, path)` pairs across calls are reported as skipped but do not fail the call. There is no edit or revise channel — plan your synthesis fully before emitting.

**Injection Source Probing (for Section 9).** Where an input vector shows injection-relevant behavior, characterize it with focused probes (never destructive payloads at this stage):
- **SQL injection shape:** single-quote probes producing SQL errors, boolean differences (`' AND 1=1--` vs `' AND 1=2--`), or timing differences.
- **Command injection shape:** metacharacter probes (`;`, `|`, `` ` ``) producing shell errors or output anomalies.
- **Path traversal / LFI shape:** `../` sequences producing file-content or traversal errors.
- **SSTI shape:** template expressions (`{{7*7}}`, `${7*7}`) producing evaluated output.
- **Deserialization shape:** serialized-format probes producing parser errors.
Record each as a candidate source with the entry parameter, the probe that produced the signal, and the observed response evidence.

**Network Surface Focus (applies to every tool):** Only emit components, endpoints, input vectors, and injection sources that are reachable through the target web application's network interface.
