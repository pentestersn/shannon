# Black-Box Vulnerability Analysis Procedure: Server-Side Request Forgery (SSRF)

NOTE ON "FOR ALL": whenever an item begins with "for all …", use the `todo_write` tool to create a separate task for each relevant endpoint/flow that needs to be probed.
From `.shannon/deliverables/recon_deliverable.md`, derive your worklist from URL-shaped parameters and request-making features (webhooks, avatars-by-URL, imports, link previews, proxy endpoints).

Every check below is performed by **submitting a crafted destination value and observing the response**. Record a baseline (a benign, public, in-scope destination or the endpoint's empty/default behavior) before probing. A signal is a difference from baseline that is attributable to the destination you supplied.

## 1) Identify Request-Making Surfaces
- For all endpoints that accept URL parameters, callback URLs, webhook URLs, or file paths, observe what the application does with them.
- Surfaces include: URL fetching (link previews, avatars-by-URL), webhook calls, API proxying, file downloads by URL, import-from-URL features.
- The signal that a surface performs an outbound request: destination-dependent error text, destination-dependent timing, or destination content appearing in the response.
**If destination input visibly influences an outbound request → classify:** `URL_manipulation` → **suggested attack:** internal_service_access.

## 2) Protocol and Scheme Validation
- For all outbound request surfaces, submit a small matrix of schemes (`https://`, `http://`, `file:///etc/hostname`, `gopher://`, `dict://`) and observe the response for each.
- Observe whether rejection is scheme-specific (an allowlist) or pattern-based (a blocklist), and whether errors distinguish "scheme not allowed" from "fetch failed".
**If dangerous schemes processed → classify:** `url_manipulation` → **suggested attack:** protocol_abuse.

## 3) Hostname and IP Address Validation
- Submit destination values pointing at loopback and private ranges (`http://127.0.0.1/`, `http://localhost/`, `http://10.0.0.1/`, `http://192.168.1.1/`, `http://169.254.169.254/` metadata host, IPv6 loopback `http://[::1]/`) and observe responses.
- A probe that returns a destination-specific error ("connection refused", "no route", timeout) evidences that the server attempted the connection — record the exact text.
- A probe refused uniformly ("URL not allowed") evidences a destination guard — test a few bypass variants (decimal/ octal / hexadecimal IP encodings, `0.0.0.0`, `0177.0.0.1`, `127.1`, `[::ffff:127.0.0.1]`) before concluding the guard holds.
- DNS rebinding cannot be tested without external infrastructure — record as a blind spot.
**If internal destinations attempted → classify:** `service_discovery` → **suggested attack:** internal_service_access / cloud_metadata_retrieval.

## 4) Port Restriction and Service Access Controls
- Where a destination signal exists, submit a few common internal service ports (`:22`, `:25`, `:3306`, `:6379`) on a loopback host and observe whether error text or timing differentiates them (refused instantly vs. filtered timeout vs. accepted) — this evidences reachability without extracting any data.
- Do NOT sweep ports broadly in this phase; three or four probes establish the signal.
**If port-differentiated signals observed → classify:** `service_discovery` → **suggested attack:** port_scanning / cloud_metadata_retrieval.

## 5) URL Parsing and Validation Bypass Techniques
- Test URL parsing inconsistencies that could bypass observed filters: URL encoding, double encoding, userinfo tricks (`http://expected-host@127.0.0.1/`), Unicode normalization.
- Redirect-following behavior cannot be fully tested without a controlled redirect target — record as a blind spot; where the surface fetches a URL you supply and renders the result, note that redirect-following remains untested.
**If bypass signals observed → classify:** `url_manipulation` → **suggested attack:** filter_bypass.

## 6) Request Modification and Headers
- For webhook/proxy surfaces, observe whether custom headers or methods can be attached to the outbound request through the feature's own options.
- Where the surface forwards the authenticated session, note whether outbound requests appear to carry application credentials (e.g., an API-proxy feature that forwards your Authorization header).
**If forwardable credentials observed → classify:** `api_proxy_bypass` → **suggested attack:** credential_theft.

## 7) Response Handling and Information Disclosure
- Observe whether outbound errors leak internal network information (hostnames, IPs, ports in error text) — this alone is a disclosure signal.
- Classify the SSRF flavor from observation: **non-blind** (fetched content appears in the response), **semi-blind** (destination-specific errors or timing only), **blind** (no observable difference — in which case you have no finding; record the surface in blind spots).
**If content returned or internal details leaked → classify:** `file_fetch_abuse` → **suggested attack:** data_exfiltration.

## **Signal-Based Analysis Methodology for SSRF (black-box)**

**Goal:** Identify vulnerable surfaces by driving crafted destinations through every URL-accepting feature and classifying the observable signals. Optimized for **classic**, **semi-blind** detection; honestly records **blind** surfaces as unconfirmed.

**Core Principle:** A destination value is assumed dangerous until the observed response proves the server restricts destinations — and a refusal of one shape is not proof for all shapes.

### **1) Create a To-Do Item for Each URL-Accepting Surface**
Use the `todo_write` tool to create a task for each discovered surface (any feature that plausibly performs a server-side request with a user-supplied destination).

---

### **2) Probe Each Surface (Forward Signal Analysis)**

For each surface, establish a baseline, then submit the probe matrix (scheme → host → port → bypass variants), recording for every probe: the exact value submitted, the response status, the distinctive response snippet (error text verbatim), and the elapsed time.

- **Signal classes, in order of strength:**
    1. **Content signal:** the response contains content fetched from your supplied destination (non-blind).
    2. **Error signal:** the response contains destination-specific error text naming the host/port you supplied.
    3. **Timing signal:** reproducible elapsed-time differences that track the destination (fast-refused vs. filtered-timeout vs. hanging).
- **Defense mapping:** for each refusal, record whether it names the rule ("scheme http not allowed", "host not in allowlist") or is generic, and which bypass variants it does or does not stop.
- **Flavor classification:**
    - **Reflected/Classic SSRF:** immediate response returns fetched content or destination errors.
    - **Stored SSRF:** the destination is persisted (webhook URL saved in settings) and the request fires later or on trigger — observe the trigger response.
    - **Semi-blind:** errors/timing only.
    - **Blind:** no observable difference — not a finding; record as a blind spot.

---

### **3) Make the Call, Document, and Score Confidence**

- **Vulnerable:** a destination signal was observed and observed defenses did not neutralize its bypass variants.
- **Safe:** every probe class was neutralized, including bypass variants.

Confidence levels:

- **High:** Content or destination-specific error signal, reproduced, with defense behavior mapped.
- **Medium:** Timing-only signal, or a signal under partial defense interference.
- **Low:** Suspicious surface (destination-shaped parameter, generic errors) without a repeatable discriminator.

---

### **4) Documentation**

- **Vulnerable paths** → add to exploitation queue, include a minimal `witness_payload` (e.g., `http://127.0.0.1:22/`).
- **Safe paths** → log in "Vectors Analyzed and Confirmed Secure" in your analysis deliverable.
- **Blind surfaces** → record in blind spots with what was attempted.

# Confidence scoring (analysis phase; applies to all checks above)
- **High** — The flaw is directly established by a reproduced, destination-attributable signal with no material alternate explanation. Scope is clear (which endpoints/parameters).
- **Medium** — The signal is strongly indicated but with at least one material uncertainty (timing-only, partial defense coverage, single-shot).
- **Low** — The flaw is plausible but unverified (indirect evidence, unclear scope, or inconsistent indicators).

Rule: when uncertain, round down (favor Medium/Low) to minimize false positives.

# Documenting Findings (MANDATORY)
For each check you perform from the list above, you must make a final **verdict**.

- If the verdict is **`vulnerable`**, you must include the finding in your exploitation queue.
- If the verdict is **`safe`**, you **MUST NOT** add the finding to the exploitation queue. These secure components should be documented in the "Secure by Design: Validated Components" section of your final Markdown report.
</methodology>

<false_positives_to_avoid>
- **Counting client-side restrictions:** Do not consider JavaScript URL validation as a defense; server-side enforcement is required.
- **Assuming from client hints:** Do not treat UI copy, placeholder text, or documentation as evidence of destination validation; require observed behavior.
- **Over-testing:** Do not extract internal data or cloud metadata content in this phase; limit to destination probes and response observation. No out-of-band callback infrastructure.
- **Timeout as evidence:** Do not assume timeout responses indicate successful SSRF without a reproducible, destination-attributable pattern (compare refused vs. filtered vs. allowed shapes).
- **Generic errors as signal:** A uniform "invalid URL" for every probe is a refusal, not an outbound attempt; do not count it as evidence of SSRF.
- **Inferring fetch without a signal:** A URL-shaped parameter is only a candidate; without a content, error, or timing signal it is a blind spot, not a finding.
</false_positives_to_avoid>
